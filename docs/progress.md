### Что поняли на занятиях
- Роли Module / Controller / Provider (Service), DI.
- Query string передаёт строковые значения; TypeScript-тип сам по себе не валидирует HTTP-ввод.
- Query-параметры, совмещённые фильтры, offset pagination, различие `total` и размера страницы.
- `DefaultValuePipe` должен выполняться раньше `ParseIntPipe`, если параметр необязателен.
- DTO-класс и runtime-декораторы; `class-transformer` преобразует значения, `class-validator` проверяет их.
- Без `@Type(() => Number)` строка `page=5` в нашем DTO не пройдёт `@IsInt()` при текущих настройках без неявной конверсии.
- OpenAPI — машиночитаемый контракт; Swagger UI — интерактивное представление. Документационные декораторы не валидируют запрос и не гарантируют соответствие фактического ответа схеме.
- `HttpException` передаёт ожидаемый HTTP-статус, а обычный `Error` без специальной обработки становится 500; `@Catch()`, `ArgumentsHost`, `getResponse()` и глобальный фильтр стандартизируют ответы и защищают детали внутренних сбоев.

### 3.1. SQL и реляционная модель — пройдено

### 3.2. Транзакции, блокировки и изоляция — практические основы пройдены
- [x] `09-transactions.sql`: `BEGIN`, `COMMIT`, `ROLLBACK`; вручную разобрана разница подтверждения/отката. Блок с `ROLLBACK` в сохранённом файле закомментирован; результат его запуска известен со слов разработчика.
- [x] `10-seat-booking.sql`: таблица `seats`, FK на `events`, `CHECK(status IN ('available', 'reserved'))`, `UNIQUE(event_id, seat_number)`.
- [x] Разобраны блокировки `SELECT ... FOR UPDATE` и то, что обычный `SELECT` не ждёт row lock; конкурентный `UPDATE ... WHERE status = 'available' RETURNING *`, семантика `UPDATE 1` / `UPDATE 0`.
- [x] Разобрана интерпретация HTTP `409 Conflict` для уже занятого места и `404 Not Found` для отсутствующего места: `UPDATE 0` сам по себе не различает причины.
- [x] `11-isolation.sql`: подготовка `isolation_lab`, `ON CONFLICT`; в двух консолях вручную проверено различие `READ COMMITTED` и `REPEATABLE READ`.
- [x] Объяснён реальный кейс согласованного многозапросного отчёта при `REPEATABLE READ`.
- [ ] `SERIALIZABLE`, `deadlock`, retry сериализации и более сложная конкуренция — **осознанно отложены**.

**Границы подтверждения:** SQL-файлы — учебные скрипты, а не повторно запускаемые миграции. `CREATE TABLE` и часть `INSERT` при повторном запуске могут завершиться ошибкой или добавить дубликаты; `03-update-delete.sql` предполагает конкретный ID 4, который не гарантирован последовательностью. Текущая БД — локальное состояние разработчика: GitHub хранит только SQL-файлы, не состояние таблиц. Автоматически SQL и две конкурирующие сессии ассистентом не запускались.

## Правила обучения и учёта прогресса

- Сначала теория: проблема → внутренний механизм → альтернативы. Потом самостоятельное ТЗ и команды проверки.
- Не писать готовую реализацию за разработчика, пока он сам её не запросит; сначала давать небольшие подсказки.
- Не зацикливаться на косметике; приоритет — Backend, PostgreSQL, безопасность и конкурентность. Автотесты в текущем темпе обучения отложены по запросу разработчика.
- Код в Git ≠ прошедшие тесты. Явно отделяем подтверждённую работу от предположений и незавершённых проверок.
